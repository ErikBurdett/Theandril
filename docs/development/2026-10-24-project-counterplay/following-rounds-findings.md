The cause is bounded and visible: `reviewProjectCounterplay` intentionally considers active projects with a newly establishable siege. The project is now paused and already under Reedbound's siege, so later `planDiplomacy` falls back to ordinary peace valuation. The accepted treaty removes that siege, allowing the same paid project to complete. The Watch trace demonstrates this through ordinary commands; no claim is made that this explains any headline pacing difference.

A follow-up policy should consider an observed near-complete enemy project paused by the observer's actual existing siege before accepting or offering a treaty that would remove it. It must retain strictly-sooner own-project and binding-treaty safeguards, avoid treating every paused project as siege-controlled, and avoid indefinitely refusing peace for unrelated blockers. Whether exact resumption conditions need another canonical query is still a design question. This probe establishes the failing sequence, not that broader policy's correctness. No runtime change is authorized by this diagnostic itself.
