# Group patrol worker implementation evidence

The worker adds one explicit `groupPatrol` transport request for existing `setPatrolEnabled` and `clearPatrol` commands. It does not create a canonical batch command, change a rule/schema, edit routes, create patrols, or add a turn/frame hook. Rules/save 35 remain unchanged. Source hashes are in `worker-source.json`.

Before the first ordinary command, the worker checks a safe request ID, exact envelope keys, dense 1–128 command array, strict canonical command shape, one current seat faction, distinct army IDs, one action and (when applicable) one enabled value, and an eight-character current campaign hash. Watch, victory, battle and capture state retain the existing player-order guards. All validated commands execute in stable army-ID order; ownership, existence and patrol-policy refusal remain canonical decisions, including partial success. Existing request kinds keep their original allowed commands.

A completed batch emits one final state and at most one autosave. Zero accepted commands do not autosave; their ordinary refusal records remain in the journal. Storage failures explain that autosave failed while preserving the accepted in-memory campaign. Recorder failure stops the loop immediately, reports only already completed results, does not autosave an uncertain history, and locks further commands/save/export pending restore. Failure publishing a final result also locks, preserving the accepted autosave where one exists. The client request ledger snapshots IDs/faction, demands exactly one sorted result per submitted ID with a nonempty refusal message, rejects missing/extra/duplicate/wrong-faction/malformed replies, isolates old IDs, and treats explicit partial-error replies as recovery rather than success.

`worker-focused-final.log`: 11 tests across two files pass in 2.17 s. These execute the real worker module with only message transport replaced, real simulation/journal/persistence and structured-clone transfers. The 128-policy authored exercise records ordinary set-patrol and route commands before batching pause, resume and remove; each batch is compared to an ordinary-command mirror, exact serialized state, journal order, replay and automatic-save restore. Every army and the nonempty existing route remain byte-equivalent in canonical data. Other cases prove complete preflight refusal, partial canonical refusal, watch denial, recorder-after-mutation stop/lock/manual restore, publication failure/accepted autosave restore, all-refused/no-save behavior and failed storage without false rollback. Request-ledger tests separately cover correspondence and stale/reset/error behavior. This is bounded authored coverage, not an organic mature-realm or browser acceptance claim.

`worker-typecheck-initial.log` and `worker-lint.log` are successful. Initial focused attempts are retained: missing required journal options, incorrectly reading the canonical route record as an array, and missing `from-save` coverage for the authored watch snapshot. Corrections changed fixture construction/assertion access only; final assertions, canonical commands, recording and restore checks were retained. No failed attempt was presented as a runtime regression.

Transport validation/result correlation is O(k log k) for sorting and O(k) additional metadata, k≤128. Dispatch runs k existing canonical commands, each retaining its existing patrol lookup, reconciliation, journal and hash work. No claim of O(k) total simulation cost is made. One final observation/packed cell publication and at most one autosave replace k individual publications. `groupPatrolResultBytes` measures the UTF-8 JSON result wrapper included in the existing transfer metric; it is zero for unrelated publications. This test duration is not a worker/frame/whole-turn performance measurement. Browser, integrated full suite, workload measurements and deployment remain parent-owned.
