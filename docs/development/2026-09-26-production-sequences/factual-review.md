## Player behavior and failure limits

The article correctly separates three concepts: campaign-owned saved selections,
personal browser/origin-local production lists, and paid canonical queues. It
states that selecting/recalling a template gives no orders and that Apply is
explicit. The limits match source: twenty-four personal templates, names of up
to forty UTF-16 code units, one to five known editor items, and a batch of up to
128 owned hearths. Building entries are unique in the editor; recruitment can
repeat. There is no template synchronization, campaign-export inclusion or live
cross-tab refresh.

The worker retains stable hearth ID order and authored item order. It appends to
existing queues and spends normal coin immediately. Each refusal stops only that
hearth's remaining list; completed hearths leave the selection, while partial or
refused ones remain. The warning that a second manual Apply submits the whole
current list and can repeat a previously accepted unit is accurate. It does not
promise automatic resume, refund, replacement or rollback. A newly queued
prerequisite building is explicitly distinguished from a completed prerequisite.

Source and tests support preserved direct controls during preference reads/writes
and failures, fresh-session Retry, unchanged invalid records, detached item arrays
and transactionally serialized competing writes. The library's post-write refresh
failure honestly reports an already-committed preference change. These operations
have no game-command path; the explicit campaign action is separate.

The recovery description matches the corrected main thread: result rows must
match the submitted hearths and item order before success; uncertain replies or
publication/recording interruption require saved recovery. The real source defect
found in review was the current-worker crash path initially clearing pending work
without setting the recovery lock. The corrected source ignores stale-worker
errors and sets the lock before rejecting pending production. The affected
browser run includes a fault injected only after the real worker paid and
recorded the work; it restores the actual earlier manual save before retrying.
