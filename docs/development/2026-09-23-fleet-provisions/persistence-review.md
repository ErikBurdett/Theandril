# Fleet provisions: independent persistence review

**Verdict: no actionable persistence defect found in the reviewed scope.** Reviewed on 2026-09-23 by the UI/browser agent, who did not author the save, chronicle or storage implementation. This was a read-only source review and an independent integrity check of the retained rules30 fixture; no production code or tests were changed.

- **Current saves and hashes retain stores.** [save.ts](../../../packages/sim/src/save.ts) validates optional integer provisions from 0 through 8 on naval armies only, includes present values in the canonical payload, and restores the parsed army objects without dropping that field. Zero remains present. Omission remains omission and is interpreted by current gameplay as full stores. Serialization and hashing reject invalid values or stores attached to land passengers. The current rules/save version and all reviewed archive/storage version registries include 31.
- **Historical input is checked before migration.** Rules28–30 use their strict pre-provisions army schema before the envelope is upgraded. A correctly resealed rules30 save containing a provisions field is therefore refused rather than silently normalized. Historical serialization and hash projections also reject populated stores, including zero; the command boundary refuses executing historical rules against such a state. [Compatibility tests](../../../packages/chronicle/src/fleet-provisions-compatibility.test.ts) cover the old-envelope rejection, malformed values, checksum tampering and every historical projection from 4 through 30.
- **Old history remains sealed while new turns use rules31.** The chronicle registries accept 31 without changing prior record shapes. Replay still selects each record's explicit rules and checks that record's matching checkpoint version; archive validation forbids version downgrades. The retained tests compare the original origin string and complete old record prefix after continuation, then replay the mixed history to the exact modern save. [IndexedDB/export coverage](../../../packages/persistence/src/fleet-provisions.test.ts) carries that same mixed archive through save, restore, compressed export/import and replay. The storage change only admits the additional version in validated headers; it does not rewrite history blobs.
- **Removing a fleet cannot leave a separate provisions entry.** Stores belong to the army object, not an external register. The existing warfare removal path deletes that object, and cargo reconciliation removes lost passengers, transport links and routes. Canonical serialization enumerates surviving army objects. Existing naval casualty tests verify missing carrier/passenger armies, empty transport links and a loadable aftermath; the new composition test additionally verifies that a merged-away source leaves a loadable result with the destination's conserved stores. No new orphan-state cleanup is required for this field.

I independently decoded all six retained rules30 cases and recomputed both the SHA256 of each original save string and its UTF-16 FNV seal. All match the captured values. All six envelopes remain version30 with no provisions field, and their 0/4/0/4/16/17 recorded-command prefixes remain explicitly rules30. The capture script refuses execution outside rules30/content `015468d1`, preventing an ordinary regeneration from the new rules.

The [final headless log](tests-final.log) records **1,861 passing tests across 232 files**. I inspected the relevant new tests and that retained result rather than rerunning the suite concurrently. This review covers persistence/version boundaries and fleet removal ownership; it does not establish complete naval AI behavior, campaign pacing or overall 1.0 acceptance.
